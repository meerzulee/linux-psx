# Why the Baikal 6.18 stack contains these fixes

This is the curated kernel history for one PS4 Slim, Baikal B1, with Orbis
12.02 handoff and an external USB root. It distinguishes intermediate
failures from the later working sequence. Sources are the old
[6.18 port record](https://github.com/meerzulee/linux-ps4/blob/386df1ad97d92defee1794bf961a0e2f5dc85a1b/docs/6.18-PORT.md),
[v12 result](https://github.com/meerzulee/linux-ps4/blob/386df1ad97d92defee1794bf961a0e2f5dc85a1b/checkpoint/docs/research/2026-05-09-v12-MILESTONE.md)
and [v60 result](https://github.com/meerzulee/linux-ps4/blob/386df1ad97d92defee1794bf961a0e2f5dc85a1b/checkpoint/docs/research/2026-05-10-v60-skip-tx-enable-result.md).
Individual source hashes and dispositions are in
[`provenance/knowledge-migration.json`](../../../provenance/knowledge-migration.json).

## MSI needs routing and actual southbridge programming

The older 6.15 investigation first tried several MSI-domain/composer theories.
An experimental branch's custom sentinel composer appeared plausible but did
not establish working device interrupts. The later v12 combination retained
the standard x86 composer, routed child allocations through the PS4 MSI parent
and programmed Baikal's per-function redirection. Correct PCI function
extraction mattered: a leaf IRQ's `hwirq` cannot be interpreted as the parent
domain's full Baikal encoding.

With interrupt remapping disabled in that measured boot profile, USB and SATA
started completing work. Counting calls to a historical Baikal demultiplexer
had been misleading: the relevant proof was device completion and the actual
active interrupt path. Do not revive an intermediate composer patch because
its trace looks busy.

The 6.18 baseline carries the three related southbridge changes together:
`0007` routing/MSI-parent adaptation, `0008` per-function programming and
`0009` composer-default restoration under `0200-ps4-drivers/`. Their upstream
and local lineage is retained in the
[patch ledger](../../../provenance/linux-ps4-ledger.md). These changes do not
prove complete interrupt parity: later hardware still logged
`No irq handler for 0.227`, and ICC needed a polling fallback.

## ACPI and display prerequisites

The local IRQ9 quirk allocates the missing ACPI SCI descriptor before ACPI
subsystem initialization on the PS4's null legacy-PIC path. The accompanying
SCI adaptation uses the tested non-threaded request path on this platform.
Those fixes address the failure chain that prevented reliable ACPI/ATOM
operations; they do not remove the need to inspect later bridge transactions.

On Liverpool/Gladius, the tested display strategy preserves the
firmware-trained GPU-to-MN864729 DP transmitter state. Standard transmitter
DISABLE and ENABLE operations each destroyed lane lock in the older v58–v60
step-by-step observations. Patches `0031` and `0032` skip those destructive
operations for the narrowly selected PS4 DP path while keeping the other
modeset operations. The bridge is not a normal monitor-side DPCD training
target. Combining an unrelated retraining strategy with this preservation
strategy would need a separate measured candidate.

## The 6.18 evidence ladder

| Checkpoint | Change or observation | What it established |
| --- | --- | --- |
| A19, 50 patches | MSI parent and external USB/root/userspace worked; ICC timed out | Booting userspace did not establish working display |
| A25, 51 patches | Added existing ICC polling fallback; replies completed (`ret=20`) | ICC progress; exposed static DRM bridge lifetime corruption |
| A28, 52 patches | `0034` used managed bridge allocation/registration | Removed the observed kref/use-after-free path; monitor still black |
| A38, 53 patches | `0035` measured bridge queue timing and lane state | Lane values `60f8=ff`, `60f9=1b` remained locked; completed userspace still gave no picture |
| A43, 54 patches | `0036` restored lane, HDMI-update and PLL/finalize transaction boundaries | Visible 1080p XFCE, successful staged queues and `10f6=d5` in the tested sequence |
| A51, unchanged A39 kernel | Repeated HDMI/XFCE and MT7668 association/SSH | A second successful boot; the separate true-cold-boot acceptance gate remained pending |

The staged MN864729 sequence was the decisive measured difference after A38.
It supports that sequence on this console and boot set; it does not prove a
universal explanation for every black-screen symptom. EDID handling, bridge
registration, GPU lane state and physical display output are separate checks.

The managed-lifetime `0034` adaptation was derived locally from the 6.18 API
warning. rmuxnet had already implemented the same core managed-lifetime
pattern in commit `3a8f6997c56b64321f3ced03886a2dda69835cb6`; that prior art
is credited in [CONTRIBUTIONS](../../../docs/CONTRIBUTIONS.md) and
[CREDITS](../../../CREDITS.md). The frozen patch bytes remain unchanged.

## Carrying this forward

Keep the 54 baseline patches in order and apply a forward-port to a new
explicit target. Preserve the accepted sequence before testing optional EDID,
GPU-reset, fan, IRQ or bridge changes. Do not enable old tracing/manual-PLL
experiments by copying all files into `series`: many were negative results,
and the preserved disabled/candidate files are intentionally inactive.

Use [CONTRIBUTING](../../../CONTRIBUTING.md) for a new source candidate and
[HARDWARE-TESTING](../../../docs/HARDWARE-TESTING.md) for a coherent bounded
hardware experiment. A renamed or firmware-free rebuild needs its own exact
artifact identities, complete module tree and acceptance record.
