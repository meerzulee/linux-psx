# Saved preparation result binding

`extract.py` binds the future preparation test's saved artifacts. It performs
no SSH, console, UART, session, mount, privilege, installation or build action.
Its stage validation deliberately reuses the existing offline `zstd` archive
checks in `common.load_inputs`; that is the only subprocess-bearing workflow
it invokes.

The narrow positive result is:

```
status: PREPARATION_USERSPACE_OBSERVED
preparation_userspace_observed: true
hardware_acceptance: false
decode_demonstrated: false
accepted: 0
```

That result requires every binding and positive observation below. It does
not promote hardware support, demonstrate decode, increment acceptance, or
make a kernel-binary/host attestation. A label or an agent's agreement cannot
create the result. No real future experiment or approval is created by this
tool or its documentation.

## Stage and observation contract

The public API always calls both `common.validate_reviewed_handoff` and
`common.load_inputs` against the explicit stage and exact review/plan hashes.
This validates the frozen bundle, corresponding-source references, complete
module archive, reviewed contract and current/saved tool bytes. There is no
CLI option to skip these calls.

The data-only observation contract must include these additional fields:

```json
{
  "expected_pci_bdf": "0000:00:01.0",
  "expected_driver": "amdgpu",
  "required_pid1_comm": "systemd"
}
```

These are expectations in the reviewed plan, not observations. The selected
numeric debugfs directory is supplied explicitly at collection time and is
bound to the BDF through the before/after DRM `name` reads. No directory 0
assumption or discovery is made. The expected root-filesystem UUID comes from
the plan's already-pinned media identity, not a presumed `/dev/sda2` name.

The contract needs these tool roles, with exact `{path, sha256}` rows:

| Role | Source |
| --- | --- |
| `acquisition` | `acquire.py` |
| `evaluator` | `observation.py` |
| `capture_evidence` | `capture_evidence.py` |
| `uart_evidence` | `uart_evidence.py` |
| `journal_collector` | `journal_bracket.py`, including its renderer |
| `result_binding` | `handoff/extract.py` |

The five dependencies are pinned in `extract.py`; the binder's own bytes must
match the contract and reviewed stage. Extra roles are permitted only through
the existing exact stage/contract/source-copy checks, and the complete tool
mapping must also match the host transport receipt.

## Existing runtime receipts

The binder reads these saved files from `stage.parent/runtime/`:

```
install-started.json
install-receipt.json
install-complete.json
install-command.json
install-before-boot-fsck.json
install-before-root-fsck.json
install-after-boot-fsck.json
install-after-root-fsck.json
session-start.json
```

It checks the current experiment/review/plan pins; held-launch installation
record; the exact five-file before/after hashes; committed and unmounted
installation; the complete 55-file/41-kernel-object staged module set; the
recorded installation count and generated module-index names; preserved
prior module counts; media UUID/size/type; all four successful read-only fsck
command receipts; and the final completion flag. The original installer
stdout must parse to exactly the saved install receipt, and its argv must
identify the reviewed apply operation, stage, serial and review pins.

The module scope is limited deliberately: the installer verifies all staged
file bytes before rename and all `.ko` bytes after `depmod`. It records the
names of generated indexes, not their final hashes. The binder does not
invent a post-`depmod` index-hash attestation.

`session-start.json` is the original runner command receipt, with exactly
`argv`, `exit_code`, `stdout`, `stderr`. Its stdout is parsed in the UART
program's actual format. The experiment label, source path, capture
generation, connection epoch and comma-formatted start offset must match the
completed session metadata. Caller labels alone are insufficient. The full
raw extract's length/fences/hash and completed continuity are checked by the
reviewed UART evaluator; the binder does not rederive the logger's event
stream or authenticate a fabricated metadata file.

## New operator launch report

The root workflow writes this record only after the actual operator report.
It is not generated by the binder. Schema 1 has exactly these keys:

| Field | Contract |
| --- | --- |
| `schema` | integer `1` |
| `kind` | `OPERATOR_LAUNCH_REPORT` |
| `experiment` | reviewed plan's experiment |
| `plan_sha256` | exact reviewed plan bytes |
| `recorded_at_utc` | aware ISO timestamp with UTC offset zero, or `Z` |
| `launch_count` | integer `1` |
| `full_poweroff_since_retained_experiment` | Boolean `true`, based on operator report |
| `retained_experiment` | experiment from the stage's exact prior plan |
| `reporter` | `operator` |
| `hardware_acceptance` | Boolean `false` |

`recorded_at_utc` is the time the launch report was recorded. It is not
represented as the physical launch instant. The power state is reported by
the operator, not measured by this program. The report must follow completed
installation and precede the host SSH capture interval.

## New host SSH transport receipt

The root workflow records the actual transport and retains its exact stdout
and stderr as separate saved files. The binder contains no SSH implementation
and does not manufacture this receipt. Schema 1 has exactly these keys:

| Field | Contract |
| --- | --- |
| `schema`, `kind` | integer `1`, `SSH_PREPARATION_CAPTURE` |
| `experiment`, `plan_sha256`, `reviewed_handoff_sha256` | exact reviewed identities |
| `observation_contract_sha256` | reviewed contract hash |
| `observation_tools` | the plan's entire role-to-SHA256 mapping |
| `transport` | `ssh` |
| `ssh_target` | explicit recorded endpoint, one nonempty token, at most 255 characters |
| `remote_argv` | exact argv shown below |
| `remote_program_sha256` | recomputed renderer result |
| `acquisition_source_sha256` | reviewed `acquisition` role hash |
| `journal_source_sha256` | reviewed `journal_collector` role hash |
| `stdout_sha256`, `stdout_bytes` | exact outer collector JSON stdout bytes, including its LF |
| `stderr_sha256`, `stderr_bytes` | exact transport stderr bytes, including empty output |
| `returncode` | integer; only zero can support the positive result |
| `started_at_utc`, `ended_at_utc` | aware UTC host timestamps, nondecreasing |
| `started_monotonic_ns`, `ended_monotonic_ns` | nonnegative integer host readings, nondecreasing |
| `expected_release` | reviewed plan release |
| `expected_pci_bdf` | reviewed observation-contract BDF |
| `status_path` | one exact canonical `/sys/kernel/debug/dri/NUMBER/amdgpu_ps4_live_prepare` path |
| `hardware_acceptance` | Boolean `false` |

The argv is the list returned by `extract.remote_argv(release, bdf, path)`:

```text
python3 -B -I - --expected-release RELEASE --expected-pci-bdf BDF --status-path PATH --include-pid1-comm
```

The remote stdin program's hash is recomputed by calling the reviewed
`journal_bracket.render_remote_program(acquire_bytes, journal_bytes)` with
the exact stage-bound source bytes. A receipt claiming an arbitrary program
hash is insufficient. This does not authenticate a hostile host or replace
the primary's actual SSH execution record.

The UTC ordering must be:

```
bounded session start
  <= installation start <= installation complete
  <= recorded operator launch report
  <= host capture start <= host capture end
  <= bounded session close
```

Session timestamps may carry another explicit timezone and are converted to
UTC. Host/operator timestamps must explicitly be UTC. Host times are not
equated with PS4 wall clocks. No physical launch/report latency is claimed.

## Outer capture and journal binding

The saved outer JSON must replay exactly through the frozen collector using
injected saved readers, uname, clocks, embedded acquisition and journal-runner
values. All raw envelopes are decoded and rehashed; complete read bounds,
sources and clock types are checked. The full regenerated object must equal
the saved report, including its flags, parsed values, source pins, ordering,
argv, query limits and error metadata. No native collector adapter is called.

The embedded acquisition independently passes `capture_evidence.evaluate`,
which replays the actual acquisition producer and checks the complete ordered
boot policy plus the cached observation contract. Outer boot IDs and releases
must agree with that validated capture. Inner monotonic/uptime observations
must fit the enclosing remote brackets. PID 1's exact read must be
`systemd\n`. These are sequential observations, not an atomic snapshot or
binary attestation.

The journal stream is bounded JSON-lines. Duplicate keys, nonfinite numeric
values (including numeric overflow), partial final lines
and non-string `MESSAGE`, `_BOOT_ID` or `_TRANSPORT` fields are rejected. Each
record must have the matching current boot ID in 32-hex form and transport
`kernel`. A stream reaching 64 entries is rejected as potentially truncated,
even when it contains the expected lines.

The journal must contain exactly one MAP and one PREPARED message matching
the UART's exact message bodies. Only the UART printk timestamp is removed;
transport CRLF is normalized. PTE values and every other message field must
remain identical. Original journal order is preserved: `--grep` with
`--lines=64` reverses output, so journal/UART order equality is not required.
PTEs are corroboration, not guaranteed nonces. Journal receive timestamps are
not treated as printk or cached proof timestamps.

## Positive normal-userspace evidence and outcomes

The UART evaluator scans the **entire** raw bounded session for faults,
parks, unexpected old probes and invalidation. The binder additionally
requires timestamped positive records for:

- `Run /init as init process`.
- The expected plan UUID in an `EXT4-fs (...): mounted filesystem UUID ...`
  message; the device name is not fixed.
- `systemd[1]: Reached target multi-user.target ...` or
  `systemd[1]: Reached target graphical.target ...`, or the exact
  description-only forms `Reached target Multi-User System.` and
  `Reached target Graphical Interface.` observed with the retained rootfs.
  Require boot → init → expected root mount → normal target in line order
  with nondecreasing kernel timestamps, within 180 seconds of the recorded
  Linux boot timestamp.

An initrd target or PREPARED alone is insufficient. No particular systemd
debugfs mount-unit wording is required. Successful recorded SSH transport,
the readable device-name/cached node, PID 1=`systemd` and current-boot journal
correspondence are also mandatory.

The 180-second comparison bounds observed kernel boot progress. It does not
measure operator response time, infer a physical launch timestamp or equate
different clocks. Failure to find a qualifying milestone is reported as
`NO_USERSPACE_MILESTONE_WITHIN_180_SECONDS`, without inventing a failure cause.

Other distinct outcomes include `INVALID_CONTINUITY`,
`PREPARATION_PARKED_OR_FAILED`, `BOOT_IDENTITY_MISMATCH`,
`PREPARATION_HISTORY_INVALIDATED`, `UART_PREPARATION_HISTORY_INVALIDATED`,
`PREPARATION_STATE_CONTRADICTION`, `INCOMPLETE_OBSERVATION`,
`HOST_RECORD_BINDING_INVALID` and `STAGE_OR_SAVED_INPUT_BINDING_INVALID`.
Malformed or incomplete evidence is never promoted to acceptance.

## API and saved-file CLI

```python
result = extract.extract_saved(
    stage_path,
    reviewed_sha256=review_sha,
    plan_sha256=plan_sha,
    uart_raw_path=raw_path,
    session_meta_path=session_path,
    launch_report_path=operator_path,
    transport_receipt_path=transport_path,
    bracket_stdout_path=stdout_path,
    transport_stderr_path=stderr_path,
)
```

The API returns plain data. The CLI additionally creates one new report:

```sh
python3 -B linux-psx/experiments/ps4-uvd-live-prepare/handoff/extract.py \
  --stage SAVED_STAGE --reviewed-sha256 REVIEW_SHA --plan-sha256 PLAN_SHA \
  --uart-raw SAVED_RAW --session-meta SAVED_SESSION_JSON \
  --launch-report SAVED_OPERATOR_JSON --transport-receipt SAVED_TRANSPORT_JSON \
  --bracket-stdout SAVED_STDOUT --transport-stderr SAVED_STDERR \
  --output NEW_RESULT_JSON
```

All file paths are explicit saved regular files. Live `/dev`, `/proc` and
`/sys` paths, symlink components, parent traversal and existing outputs are
rejected. Output creation uses exclusive/no-follow open; its parent must
already exist. These path checks do not authenticate an arbitrary hostile
mount or host. The caller preserves the original artifacts identified by the
result's hashes.

## Synthetic tests

```sh
python3 -B linux-psx/experiments/ps4-uvd-live-prepare/handoff/test_extract.py \
  --report-file lab/uvd-2026-10-20/live-prepare/result-binding-tool/attempt-01/macos-03.json
```

Use a new receipt name for another run. Tests use ephemeral synthetic stage,
review, installation, transport and session records with a clearly synthetic
2099 experiment identifier. The real common validators and offline `zstd`
checks execute on small synthetic archives; all acquisition and journal
dependencies are injected fakes. Nothing starts a real experiment, creates
a real approval, installs files, contacts SSH or touches devices/UART.

The first run's failed test-interface assertion and source snapshot remain
preserved under `attempt-01/`; the final 38-test run passes. Tests and
source review remain software evidence only.
