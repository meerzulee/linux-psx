# PS4 UVD runtime memory component

This is the bounded memory component for a normal AMDGPU UVD queue candidate. It is not wired into an IP block, CS admission, firmware startup or a running driver. Its only owned source files are `amdgpu_ps4_uvd_memory.c` and `.h`. It changes no `amdgpu_device` fields; the caller embeds a zero-initialized `struct amdgpu_ps4_uvd_memory`.

## API and ownership

All functions take explicit `(adev, memory *)` arguments, and reject a state owned by another device.

1. `amdgpu_ps4_uvd_memory_prepare(adev, memory, vmid4_reserved)` validates the measured PS4 geometry, allocates/pins/maps three VRAM BOs, acquires its own extra GART BO reference/pin, and builds/readbacks the tables. The caller must have reserved VMID4 out of the normal allocator already. Passing `true` is an ownership assertion, not an allocator operation; the component also checks that the VMID4 LRU node remains empty. Reservation integration belongs to the parent driver.
2. `amdgpu_ps4_uvd_memory_map_private_gtt(adev, memory, bo, native_gpu_addr, bytes, private_va)` maps a pinned GTT BO's **prefix** into the private window. `native_gpu_addr` must equal the BO's actual native GPU address, not an arbitrary BO offset. Size/addresses must be page-aligned and the requested size must fit both the BO and its populated TTM pages. The component takes an additional pin/reference of its own. Do not call while holding that BO's reservation.
3. `amdgpu_ps4_uvd_memory_install(adev, memory)` performs full owned-table readback, saves the original VMID4 root in `original_root`, sets `entered` **before** writing the root, writes/readbacks only VMID4's root register, then issues an ordered VMID4 invalidate. `pd.gpu_addr` is the native MC address of the owned root. A failure after `entered` becomes true is irrevocable and must retain all resources. `installed` means the root readback matched and the invalidate was issued, not that UVD accepted or consumed the tables.
4. `amdgpu_ps4_uvd_memory_refresh(adev, memory)` validates the unchanged GART BO/table/address/geometry, shared context policy, VRAM physical base and installed root, then orders publication and invalidates VMID4. Shared GART leaves require no copy or PDE rewrite. Call after final BO validation and dependency waits, before the next UVD job is published, with the previous UVD job complete. The caller serializes operations against reset, GART teardown and competing invalidation/configuration work.
5. `amdgpu_ps4_uvd_memory_cleanup_pre_entry(adev, memory)` releases only the component's own pins/references/CPU metadata before entry. It returns `-EBUSY` without changing any of them once `entered` is true. A partial pre-entry cleanup failure leaves the state unprepared and retains the remaining objects so cleanup can be retried. There is no post-entry free/unpin, original-root restoration, reset, retry or rearm API.

The caller must retain the memory struct itself, the device and the GART CPU mapping after entry. An extra GART BO pin/ref prevents backing relocation/free; it cannot stop the normal GART destructor from unmapping its CPU pointer or disabling the VM hub. Parent lifecycle guards must prevent that path. Ordinary AMDGPU BO allocation can update VMID0 GART through existing TTM machinery; explicit VM register writes by this component are only VMID4 root and a VMID4-only invalidate mask. It never writes context1 controls, range registers or another VMID root. Publication uses the standard HDP flush callback.

## Layout and validation

- The supported layout is PS4 Liverpool/Gladius, 4 KiB CPU/GPU pages, context1 enabled with depth 1 / block size 10, `num_level=1`, root level PDB0, exactly eight managed graphics VMIDs, and VMID4 range `0..max_pfn-1`. It checks these controls and never changes the shared policy.
- Each leaf is 1024 PTEs / 8 KiB and covers 4 MiB. Native GART and native VRAM starts/sizes must be complete 4 MiB spans, fit the VM PFN limit and not overlap one another or the private window. The root allocation is bounded at 1 MiB, GART at 1 GiB, and VRAM at 8 GiB. Runtime counts derive from `adev`, not EXP005 addresses.
- Native GART directory entries point into consecutive 8 KiB chunks of the existing flat GART BO. Its source is checked to be pinned, contiguous VRAM, CPU-mapped, sized for the actual GPU-page count, and the table currently installed for flat VMID0. The component takes its own GART pin/ref before using it. It derives PDE addresses/flags with `amdgpu_gmc_get_pde_for_bo()`, validating the CIK address restriction before the helper's `BUG_ON`.
- Native VRAM **virtual** addresses retain their MC values. Leaf **physical** addresses use `amdgpu_gmc_vram_mc2pa(adev, vram_start) + offset`, not literal MC identity. Non-SYSTEM readable/writable flags derive from the allocated VRAM leaf BO's TTM flags and the CIK ASIC PTE helper. The whole converted physical range must fit the actual PTE mask. Parent CS admission must reject BO attributes outside this ordinary unencrypted VRAM policy.
- The separate private window is `[0x300000000, 0x300400000)`, with one owned 8 KiB leaf. Up to 16 private BO mappings are admitted, entirely before entry. The API rejects imported/external/userptr/encrypted/unpopulated/unpinned BOs, wrong native aliases, range overlap and duplicate private DMA/PFN pages. Every requested page must match the real canonical GART PTE exactly, including DMA address and flags. It validates the entire request before any private PT write. Unmapped private slots stay zero and are included in readback.
- The measured EXP005 apertures produce 128 shared GART leaves, 256 owned VRAM leaves, one private leaf and a 128 KiB root. The component does not reuse firmware storage for these allocations or assume a fence/IB address. The parent chooses the proven firmware/ring private aliases before installation; normal kernel IB/CS BOs remain reachable at native addresses through the mirror.

`refresh` deliberately does not repair a changed table/root, update private PTEs or allocate anything after entry. A mismatch is a terminal integration error for the parent queue. The standard CIK source invalidates by writing the requested VMID bit; this component follows that protocol and drains posted MMIO with a response read. It does **not** invent a response-bit completion rule, claim all-page device visibility, or prove that DMA has stopped. Normal UVD CS fences and actual multi-frame output must establish the queue's hardware behavior.

## Parent integration requirements

The default-off runtime driver gate, VMID4 allocator reservation, exact firmware/startup contract, requester VMID fields, real ring callbacks/scheduler, normal userspace BO admission and bounded pin/ref budget, private descriptor offsets and all error/PM/reset/teardown rules remain parent-owned. In particular, this component's retained objects do not protect arbitrary userspace BOs or stop kernel IB suballocations from being recycled after a timeout. A timeout must stop later publication and preserve every possibly DMA-visible BO and IB span. Disabling PM alone is insufficient.

Suggested order: reserve VMID4; prepare memory; allocate/populate and map private firmware/ring/fence BOs; install root; configure/start UVD with those descriptors; return through normal AMDGPU initialization. Before actual scheduled UVD publication, complete dependency waits and call refresh. Before entry, a preparation failure may clean up. After entry, any later initialization or job failure must follow retained failure handling, including failures that would otherwise enter AMDGPU's generic initialization unwind.
